## [0.2.0] - 2026-09-06

### Highlights

**Out of the box now means every surface, not just the binary.** 0.1.0 shipped a CLI that defaulted the model directory and downloaded the model on first use, and a library that made every caller re-derive that same path. The asymmetry was the defect: "works with no setup" was a property of one entry point rather than of the package. `Config` closes it by answering one question, once, for all three surfaces: where do things live and what are the defaults. It resolves per key from an explicit argument, then the environment, then the config file, then the defaults compiled into the crate, and it records which rung each value came from, so `matra config show` can print provenance instead of asserting numbers. The line it does not cross is the one the roadmap warned about: `Config` carries locations and defaults, never behavior. Which metrics run and how output is shaped stay where they were, because a config format that selects behavior puts policy in a file the library parses. `Engine::with_defaults()`, `Matra.english()` and `uvx matra analyze file.md` are the same idea on three surfaces, and every 0.1.0 signature still works unchanged beside them.

**One command line, two launchers.** matra had two CLIs. `src/bin/matra.rs` was the Rust one; `python/matra/cli.py` re-implemented it in click and rich so that `uvx matra` worked, and it had drifted, carrying a flag the binary lacked while ignoring `--model-dir`. The 0.1.0 changelog already records this class of defect once, when the Python CLI re-implemented passive detection and got it wrong. The fix is structural rather than a parity test, because a parity test catches drift only after it happens: the clap definition, the renderers and the exit codes move into the library as `matra::cli`, with one entry point that takes its own output sinks and never exits the process, and both launchers call it. This is also the shape maturin recommends for a crate that ships both a library and a tool. The ACES rule it settles is broader than this release: Rust is the core and every CLI, and a reach layer exposes the API and the extension points and carries no behavior of its own. `python/matra/cli.py` is now four lines of code, and `click` and `rich` left the dependency list entirely.

**Pinned downloads are one discipline, not an exception per model.** `Udpipe::english` has fetched a pinned artifact, verified it against a constant in the source, and loaded the verified bytes with no second read of the disk since 0.1.0. The reference embedding model did not, because ADR-0010 decision 6 read as "no network"; what it meant was "no unpinned network", and it is amended in place to say so. `Model2Vec::potion_base_8m` now does exactly what the UDPipe path does, against the digest `spec/` already carried, so making the semantic tier work out of the box removed an exception rather than adding a capability. The bound on the claim is the digest: exactly one artifact set can arrive this way, a mismatch over files the call downloaded removes them and retries once, and a second mismatch removes them again and fails, so a partly-trusted model is never loaded and a failed download leaves nothing behind. The provisioner only ever removes files it downloaded itself, so it downloads only into a directory holding none of the three artifacts and refuses a directory already holding artifacts that are not the pinned set, with nothing there downloaded over or deleted. `from_dir` and `from_path` still load what you name and never reach the network.

**The agent door is the program itself.** matra is run by agents at least as often as by people, and an agent about to run it needs what `--help` does not carry: what the tool is for, when to reach for it, every command with its exact JSON shape, and what each number does not license it to conclude. That could have been a page to link or a file to install by hand. It is neither, because both drift from the version actually installed, and an agent cannot tell that it is reading the wrong one. `matra --skill` prints text embedded in the binary with `include_str!`, so the instructions are the ones that build's own commands answer to, and `matra --skill -r <name>` reaches six deeper references on demand rather than spending the reader's attention up front. Two properties keep the text honest. Every `matra` command in it is extracted and run through `cli::run` by `tests/skill.rs`, with the extracted count checked against a scan of the same files, so a command that stops working fails CI the way a stale type name fails the docsite. And the files the flag prints are the files at `skills/matra/`, in the layout plugin discovery expects, so the flag and the plugin distribute one source rather than two copies to keep in agreement. The docsite stays the door for a person, with concepts, citations and benchmarks; neither door is derived from the other, and both are tested against the code.

**A wheel is a promise about someone else's machine, and matra's was three promises short.** A wheel is only useful if pip picks it, and pip picks on three axes at once: architecture, glibc, and the exact CPython the extension was compiled against. 0.1.0 satisfied one of them well. There was no Linux aarch64 wheel, which is not a niche gap but every Graviton instance, every Pi, and every Linux container on an Apple Silicon Mac, where `linux/arm64` is the default. The Linux wheel was built on the runner rather than in a manylinux container, so it inherited the runner's glibc and was tagged `manylinux_2_34`, which pip refuses on Debian 11, Ubuntu 20.04, RHEL 8 and Amazon Linux 2. And nothing declared abi3, so the wheel was version-locked to `cp312` and a machine running 3.13 or 3.14 fell through to a source build even on macOS arm64, which the page claimed was covered; `uvx matra` on 0.1.0 was observed printing `Building matra==0.1.0` for exactly that reason. Every one of the three ends in the same place, the sdist, and the sdist did not work either, because UDPipe is C++ and the installation page named only Rust. 0.2.0 answers all four. The extension builds against the CPython stable ABI (`abi3-py312`), so one wheel per platform serves 3.12 and every GIL-enabled CPython after it, including ones that do not exist yet; the Linux wheels build inside `ghcr.io/pyo3/maturin`, which drops the floor to glibc 2.17 and, on a native arm64 runner, produces the missing aarch64 wheel from the same command; and the installation page names the C++ compiler with the package to install on each platform. One gap stays open and is now named on the page rather than left to be discovered: a free-threaded interpreter accepts the `abi3t` tag and not `abi3`, and pyo3 gains the free-threaded stable ABI at 3.15, so `python3.14t` still falls to the sdist on a platform that ships a wheel. The shape is ruff's and uv's, and the reason to prefer it over a matrix across interpreters is that a matrix chases the problem once per CPython release while the ABI settles it once. What it costs is a ceiling: pyo3 features outside the stable ABI are now foreclosed, which is why `ci.yml` and `publish-pypi.yml` both assert the `cp312-abi3` tag rather than trusting it, and why the release smoke test installs each wheel under a CPython one version newer than it was built against, with pip forbidden to fall back to a source build. ADR-0014 records the trade in full.

### Added

- An end-to-end validation practice, in `.claude/skills/e2e-validation/SKILL.md`, the `newcomer` agent, and `scripts/e2e-sandbox.sh`. Everything else here tests matra against its own source tree; this covers the one question that cannot be answered there, which is whether the published artifact works for someone who has none of what we have. It is deliberately two layers that must not be confused: mechanical gates that install the built artifact and run real commands on it in CI, and an exploratory pass that produces a report a human judges and never blocks a merge. `docs/surveys/2026-09-06-release-validation.md` establishes that none of the nine comparable projects runs the second layer, and that the first is not universal either: mdBook builds a release binary per target and never executes it, and two of the rest check only that the binary starts. So the second layer is this project's own call, labelled as such rather than borrowed, and the survey is cited for what it settles rather than for the conclusion it explicitly declines to draw. Two pilot passes on 2026-09-06, one on macOS following every page and one in Linux containers, found six blocking defects that every existing gate had passed; the skill records why they were found, which is that the tester behaved like a person rather than a script. Both reports are committed at `docs/e2e/`, because a method whose grounding lives in a scratch directory is a method nobody can check, and that is the skill's own evidence rule applied to itself. The sandbox script moves `HOME` as well as the XDG variables, because a legacy model cache resolves from home and XDG alone is not a cold start. Its snapshot mode fingerprints the real locations on names, sizes and mtimes: a directory's mtime moves when an entry is added or removed, which is exactly the signal wanted, and reading a directory does not touch it. `snapshot` refuses to run inside a sandbox, guarded by both an environment variable and a marker file written before any export reaches stdout, because in there `HOME` is the sandbox and the command would fingerprint the wrong tree and hand back a false all-clear. It fingerprints the union of every location matra's three resolution tiers could name rather than following their precedence, because following the precedence and stopping one tier short produced that same false all-clear twice. The script has one property and it now has a gate: it cannot report a clean result for a tree it did not examine. `scripts/test-e2e-sandbox.sh` asserts that from `just check`, covering stdout staying empty on every induced `new` failure, both routes into the sandbox guard, a leak seeded at each of the eight union targets, a leak behind a symlinked target, and an unreadable target; it skips the cases needing a permission bit uid 0 ignores and says how many it skipped. Three review rounds each closed a hole in that property and left another, which is what an untested script buys, and run against the version before this entry the new suite fails six ways on macOS and on Debian alike. A failed fingerprint used to abort the walk after earlier targets had already reached stdout, so both snapshots of a pair were byte-identical while every target after the failing one went unexamined, and one unreadable directory under the config path hid leaks in the data and legacy paths entirely; `snapshot` now writes an `UNREADABLE` line into the artifact being diffed and carries on to the rest. `find` was stopping at a symlinked target rather than descending it, so a leak written behind the link moved the target's mtime and not the link's and the fingerprint did not change; it now runs `find -H`, which follows the named argument only. `CDPATH` turned a relative directory argument into a sandbox built inside the `CDPATH` target, with a two-line `HOME` exported and a zero exit status, which is `new` writing into the real home silently; the resolution is now `CDPATH='' cd --`. And a symlinked sandbox home put the marker into whatever the link pointed at, because `mkdir -p` is a no-op through a link, so `new` now refuses a symlinked sandbox home and one that resolves to the real home. `tests/sandbox_env_parity.rs` closes the remaining hand transcription: the set of `MATRA_*`, `XDG_*` and `HOME` variables the resolvers in `src/config.rs` read is asserted equal to the set the script names, so a resolution tier added there fails a gate rather than quietly narrowing the union, and being a Rust test it runs on every push rather than only when someone types `just check`.

The files ship in the crate and sit in the standard plugin layout, so one set of files serves both distributions (ADR-0012).

The text is embedded with `include_str!`, so an installed program prints instructions that match it rather than a copy that may have drifted, and the output is byte-identical to the file on disk from either launcher. `--skill` outranks a subcommand and needs none; `-r` without it is an error that says which flag is missing. Under `--json` the command uses the one envelope every other command uses, with `input` null because it reads no document and `result` carrying `{"name", "body"}` or `{"references": [{"name", "summary"}]}`. `--help` is otherwise unchanged; the usage line now reads `[COMMAND]` rather than `<COMMAND>`, because a subcommand is genuinely optional now. - `tests/skill.rs`, the executed-incantation test: every fenced `console` or `bash` block in the skill and its references whose first line is a `matra` command is extracted and driven through `cli::run` against fixtures in `tests/fixtures/skill/`, asserting the exit code the block annotates and, for `--json` blocks, that the output parses and carries `format_version`. The extracted count is asserted against a line-oriented scan of the same files, so a command written outside a fence raises the scan and fails the test rather than escaping the runner. Blocks annotated `<!-- needs: model -->` run in the model-gated lane. A skill whose commands do not run is a defect, not a documentation nit.
- CI gains a `cli` lane. The feature is not in the default set, so `check`, `clippy` and `test` under it had never run on a push, and the skill test lives there.
- Python: a caller's own object can be an embedder. `Matra.semantic_clusters(text, threshold, model)` takes a `Model2Vec` or any object with `embed` and `identity`, wrapped in the binding by an adapter over the `Embedder` port. The port was always the extension point; what was missing was the route to it from Python. The contract check stays in the library, so a Python embedder that returns the wrong number of vectors raises `ValueError` carrying the same message a Rust implementor would read, and an exception raised inside `embed` arrives as `ValueError` with its own text inside. The identity is read once, before the text is parsed, so a broken embedder costs one method call rather than a document's parse, and scores cannot be reattributed mid-call. This arm needs no embedding adapter compiled in: the wrapper reaches only the `Embedder` port, so the extension module clusters vectors a caller brings whether or not `model2vec` is compiled into it.
- `domain::Error::kind()`: the stable kind string for a variant, the key a consumer branches on instead of matching against a message. Exhaustive with no wildcard, so a new variant fails to compile until someone names it. The vocabulary was written in the Python binding first; it lives on the domain type now, which is what lets every crust read one list. `spec/tests/corpus/items.json` pins it, with runners in `tests/corpus_conformance.rs` and `python/tests/test_corpus_conformance.py`, and Python exports it as `matra.ERROR_KINDS`.
- Python: `Matra.analyze_path(path)` puts directory ingestion on the Python surface, `Ingest::path` into `Engine::analyze` collected in order. Each item is a `CorpusEntry` (`path`, `analysis`) or a `DocumentError` (`path`, `error`), so one unreadable file costs one item rather than the walk, and a failure listing the path itself raises instead. `DocumentError` wraps `std::io::Error` and has no serde form; the binding materializes its fields, with the error as the `kind` `Error::kind` names plus the `Display` message. Both item shapes are assembled rather than serialized, because serde refuses a non-UTF-8 `PathBuf` and one file with an undecodable name would otherwise have ended the whole walk. Every path crosses through `os.fsdecode`, so `os.fsencode` on a returned `path` names the file the walk read.
- Python: every path argument takes a `str` or an `os.PathLike` such as a `pathlib.Path`: `Matra.analyze_path`, `Matra.english`, `Matra.from_path`, `Model2Vec.from_dir` and `Model2Vec.potion_base_8m`. Callers passing a `str` are unaffected.
- Python: `Model2Vec.identity()` returns the model hash, so the built-in adapter satisfies the `Embedder` protocol instead of being a second accepted type beside it. `Matra.semantic_clusters` is annotated with the protocol alone, and keeps the direct `Model2Vec` arm as a fast path that calls no Python.
- Python: `CorpusEntry`, `DocumentError`, `ErrorInfo`, the `CorpusItem` union and the `ERROR_KINDS` vocabulary join `matra.types`, along with the `Embedder` protocol; all six are exported from the package root and typed in `_core.pyi`.
- `Model2Vec::potion_base_8m(dir)` and `Model2Vec::from_config(cfg)`: the reference embedding model without placing files by hand. The three artifacts are downloaded when the directory holds none of them, and nothing loads unless the SHA-256 over all three equals a constant pinned beside the URLs they came from, so exactly one artifact set can arrive this way. Verification happens before parsing and the verified bytes are the parsed bytes, with no second read of the disk in between. **The provisioner only ever removes files it downloaded itself.** A directory that already holds all three artifacts and does not match the pin, or that holds only some of them, is refused with `Error::ModelInvalid` naming the directory, and nothing there is downloaded over or deleted: the three filenames belong to the artifact format rather than to this one model, so they can be a caller's own. A mismatch over files this call downloaded removes them and downloads once more; a second mismatch removes them again and returns `Error::ModelInvalid`, so a partly-trusted model is never loaded and a failed download leaves nothing behind. Each artifact lands through a temporary file opened with `create_new`, so a path already sitting at that name fails the open instead of being written through, then a rename. A fetch is bounded at 300 seconds end to end and 30 seconds on the connection, and a download past 64 MiB is `Error::InputTooLarge` with `what` set to `"embedding_download"`. A download that fails at the transport or answers with a non-2xx status is `Error::Io`, with the URL in the message and the `io::ErrorKind` separating a timeout from an unreachable host. `Model2Vec::from_dir` is unchanged and never downloads.
- Python: `Model2Vec.potion_base_8m(dir=None)`, resolving the directory through the configuration when the argument is absent, exactly as `Matra.english()` does.
- `scripts/fetch-embedding-hash.sh`: fetches the three artifacts at a revision and prints the digest to paste into the adapter and into `spec/tests/semantic/reference-model.json`, the `scripts/fetch-model-hash.sh` counterpart for the embedding model. With no argument it reads the revision out of the adapter's URL constants rather than carrying a second copy of it, and it hashes with `sha256sum` where that exists and `shasum -a 256` where it does not. A unit test asserts that the digest compiled into the adapter and the one the conformance fixture pins are the same string.
- `ureq` joins the dependency tree for the `model2vec` feature on native targets. It was already there through `udpipe-rs`; the declaration is target-gated to `not(target_arch = "wasm32")`, so the wasm32 closure the adapter compiles into is unchanged and carries no network client.
- One command line, two launchers. The clap definition, the renderers and the exit codes move into the library as `matra::cli` behind the `cli` feature, with one entry point: `cli::run(args, out, err) -> u8`. It never calls `process::exit` and never reaches for the process's own streams, so a caller hands it whatever sink it wants. `src/bin/matra.rs` is now a launcher of about a dozen lines, and `python/matra/cli.py` is one of four lines of code. The program name is set explicitly, so `--help` reads the same from either.
- `matra config show` prints every resolved value with the rung it came from, one key per line in the shape `cargo config get --show-origin` uses, or as an object under `--json`. `matra config init` writes the shipped defaults to the resolved config path, creating parent directories, going through a temporary file in the same directory so no reader sees a half-written config, and refusing to overwrite an existing file without `--force`.
- `--sections` on `matra analyze`: the per-section breakdown the Python CLI had and the Rust binary did not. Nothing a user could do before this release stops working.
- `NO_COLOR` (honored when present and not empty, per no-color.org) and `--color auto|always|never`, where an explicit choice outranks the variable in both directions. `--quiet` suppresses the human-readable output and leaves the exit code alone, with no effect on `--json`. `-` in place of a path reads stdin, with `--stdin-filename` supplying the label and the extension that selects the decomposer; the 8 MiB cap is enforced while reading rather than after it, and the bytes are counted before they are decoded so an oversized input reports its size rather than a UTF-8 failure at the truncation point. `matra completions <bash|zsh|fish>` prints a completion script. `--version` names the version and then the features the build was compiled with.
- `analyze`, `summarize` and `keyphrases` take a file and refuse a directory, naming the path and the remedy. `Ingest::path` accepts a directory and yields every file in it, and these three commands report on one document, so accepting one would mean printing an arbitrary file's numbers under the directory's name.
- Python: `_core.cli_main(argv) -> int` runs the command line and returns its exit code, rendering into buffers that are then written to `sys.stdout` and `sys.stderr` so output interleaves correctly with anything Python already wrote. Arguments cross with the filesystem encoding (`os.fsencode`) rather than as text, so a `sys.argv` entry Python decoded with surrogate escapes names the same file here that it names for the Rust binary.
- `domain::Format::from_path(path)`: the extension-to-format table, on the type it produces. It was written twice, once in the file source and once in the command line, which is one copy too many for a mapping that must agree with itself. Both callers read this function now. An extension the build does not know, and a path with no extension, are `Format::PlainText`.
- `spec/tests/cli/envelope.json`: a conformance fixture pinning the `--json` envelope, with runners in `tests/cli.rs` and `python/tests/test_cli.py`. There is one CLI implementation, so what the fixture protects is the handoff at each launcher, not the behaviour behind it.
- `config::Config`: a composition-root value that resolves where things are and what the defaults are, per key, from an explicit argument, then the environment, then the config file, then the defaults compiled into the crate. It carries locations and defaults and never behavior (ADR-0011): the model directory, the semantic threshold, and the default counts and algorithm names, all of which a caller could pass as arguments instead. Paths follow the XDG conventions on Linux and macOS (`$XDG_CONFIG_HOME/matra/config.toml`, `$XDG_DATA_HOME/matra`), overridable with `MATRA_CONFIG_FILE`, `MATRA_DATA_DIR` and `MATRA_MODEL_DIR`. An existing, non-empty `~/.matra/models` is used as the model directory when the new location does not exist: matra never creates `~/.matra`, but when an existing, non-empty legacy cache is selected it is used as the model directory, downloads and re-downloads included, and creating the new location or setting `MATRA_MODEL_DIR` moves off it. An empty leftover `~/.matra/models` is not selected. A missing config file is not an error; a malformed one, an unknown key, or an algorithm name this build does not know is `Error::InvalidInput` naming the file and the key or line. `Config::sources` reports which rung every value came from as a `ValueSource`, and `Config::from_sources` takes the environment and the file contents as arguments so no test reads the developer's home.
- `Config::with_model_dir`: the argument rung, and the only thing that produces `ValueSource::Argument`. It returns the same configuration with the model directory replaced and that one key's source changed, so a caller handed a directory (a command line's `--model-dir`, say) can layer it on top without losing the provenance of every other value.
- `config/default.toml`: the defaults, shipped inside the crate and embedded with `include_str!`. A user config file overrides it key by key.
- `Udpipe::from_config`, `Engine::from_config`, and `Engine::with_defaults`: the no-setup path, additive to the existing constructors, which are unchanged. `Engine::with_defaults()` is `Config::resolve()` followed by `Engine::from_config`.
- Python: `Matra.english()` takes the model directory optionally. With no argument it resolves through `Config` exactly as the Rust surface does.
- `toml` joins the default dependency tree, with the `parse`, `serde` and `std` features only. Pure Rust; the wasm32 job confirms the core and the model2vec adapter still compile for `wasm32-unknown-unknown` with it in the tree.
- `embed` port: the `Embedder` trait (one method, `embed`, batch in, vectors out, length- and dimension-uniform by contract) and the `domain::Embedding` carrier, a serde-transparent newtype over `Vec<f32>`. Tier 2 channel discipline per ADR-0010: nothing derived from embeddings becomes a field on the deterministic pipeline's types.
- `extraction::semantic_clusters` and the `SemanticClusters` / `SemanticCluster` / `SemanticEdge` domain types: connected-component clustering over precomputed sentence embeddings, edges carried in the type so co-membership is never mistaken for pairwise similarity, singletons excluded by construction, model identity and threshold carried as provenance. Pure over domain values; tested without any model. New `Error::InvalidInput` variant for contract violations, routed to Python `ValueError`.
- `embed_and_cluster`: the composition-root pairing of a `Document` with an `Embedder` (embed the sentences, cluster the vectors, attribute the scores to the embedder's own identity). `Embedder` gains the `identity` method that makes misattribution impossible.
- Python: `Model2Vec` (load a static model, read its hash and dimensions, `embed` texts directly for the UDPipe-free path), `Matra.semantic_clusters(text, threshold, model)`, and the vectors-in module function `semantic_clusters(embeddings, threshold, model_hash)`; wheels now build with the `model2vec` feature. The package asks for it: `import matra` against an extension built without it raises `ImportError` naming the missing cargo feature and the `maturin develop` line that supplies it, rather than failing on a bare missing symbol. The FFI shape fixture lands at `spec/tests/semantic/clusters.json` with Rust and Python runners, comparison done in f32 space.
- `model2vec` feature: a static-embedding adapter loading the model2vec artifact format (safetensors matrix, tokenizer.json, config.json), loaded from files a caller supplies with no network or through the pinned download named above, hashed on load for provenance. Pure-Rust closure verified on wasm32 (a new CI job holds the line). Inference is a gather, mean pool, and optional L2 normalize, parity-tested against the Python reference; f16/i8 artifacts are rejected loudly (f32 only in this build). Panics in the parsing paths convert to `Error::ModelInvalid` at the adapter boundary.

### Changed

- Python wheels are abi3. `pyo3` gains `abi3-py312`, so the extension module is compiled against the CPython stable ABI and one wheel per platform serves 3.12 and every later 3.x on GIL-enabled CPython instead of only the interpreter it was built with. Verified end to end: a wheel built against 3.12 installs and runs under 3.14 in an image carrying no compiler and no Rust toolchain. Free-threaded interpreters are outside that promise and the installation page now says so: they accept the `abi3t` tag and not `abi3`, and pyo3 gains the free-threaded stable ABI at 3.15, so `python3.14t` builds from the sdist. The constraint this accepts is that pyo3 and CPython APIs outside the stable ABI are now unavailable to the bindings; `ci.yml` asserts the `cp312-abi3` tag on every push, guarded by a wheel count so a second wheel in `dist/` cannot slip the check, so losing the feature is caught immediately rather than at a release (ADR-0014).
- The Linux wheels are built inside `ghcr.io/pyo3/maturin`, pinned by index digest, rather than on the GitHub runner. Building on the runner made the wheel inherit the runner's glibc: the 0.1.x Linux wheel was `manylinux_2_34`, which pip rejects on glibc 2.31 with `not a supported wheel on this platform`. The container is manylinux2014-based, so the floor is glibc 2.17. `RUSTUP_TOOLCHAIN=stable` is set for that build and is load-bearing: `rust-toolchain.toml` asks for a component the image does not carry, `llvm-tools-preview`, so rustup re-syncs the channel inside the container, and the rename it performs to swap a component crosses the overlay boundary and fails with `Invalid cross-device link (os error 18)`. `RUSTUP_TOOLCHAIN` outranks `rust-toolchain.toml` in rustup's override precedence, so the build uses the toolchain already in the image and the sync never happens. The alternative, `RUSTUP_PERMIT_COPY_RENAME=1`, also works, but rustup documents it as unstable, sacrificing some transaction protections, and removable at any point, which is not what belongs on a release path.
- `publish-pypi.yml` builds four wheels rather than three. Linux aarch64 joins the matrix on `ubuntu-24.04-arm`, a native arm64 runner, so Graviton, Ampere, Pi and Linux containers on Apple Silicon get a wheel instead of a source build. Windows is still absent, for the same reason as before: the UDPipe build under MSVC is unverified, and an untested wheel is worse than none.
- The release smoke test installs each native wheel under CPython 3.13, one version newer than the wheel was built against, with `--only-binary :all:` so pip fails rather than quietly building from source. Both workflows also assert the wheel's tag directly: `cp312-abi3` everywhere, and `manylinux2014` on Linux.
- `book/src/tutorials/installation.md` names the C++ compiler among the requirements, with the package to install on Debian, Fedora, Alpine, Arch and macOS. UDPipe is a C++ library that `udpipe-rs` builds during the cargo build, so a from-source install with only a C compiler stops at `error occurred in cc-rs: failed to find tool "c++"`, and the page previously named only Rust. The page also now states the wheel matrix and the glibc floor accurately, says that Windows is untested rather than leaving it unmentioned, replaces "can take several seconds" for the first model download with the measured 3 to 35 second range, and distinguishes the two `matra --version` feature lines: `cargo install` produces `features: udpipe cli` and the wheel produces `features: udpipe model2vec python cli`, both correct for their own build. It also bounds the `uvx` equivalence claim to 0.2.0 and later and sets a version floor in the command, because 0.1.0 shipped a second CLI written in Python with a `--json` shape of its own and an unpinned `uvx matra` still resolves to it.
- `README.md` states the same wheel matrix and the same from-source prerequisites as the installation page. It previously said wheels ship for Linux x86_64 and macOS only, and that the sdist needs a Rust toolchain with no mention of a C++ compiler: both halves are false as of this release. That text is not only the repository front page, it is `readme` in both `Cargo.toml` and `pyproject.toml`, so it becomes the crates.io page and the wheel's `METADATA` for 0.2.0 and cannot be corrected after the publish.
- Attribution is one name everywhere. `Cargo.toml`, `pyproject.toml` and `book/book.toml` said `yzavyas`, `LICENSE` said `mox.nexus`, and the plugin manifest said `mox labs`: three names for one project, with the one carrying legal weight naming an entity that appeared nowhere else. ADR-0013 settles it on the organization, `mox labs <yza.v@moxlabs.org>`, and the copyright line reads `Copyright (c) 2026 mox labs`. The reason is that the repository, the homepage and the plugin manifest were already organizational, so an individual author contradicted every URL printed beside it, and registry metadata is immutable per version: a name published wrong cannot be edited, only superseded. Commit authorship is untouched and still records who did the work.
- ADR-0010 decision 6 amended in place. "No network" was the wrong reading of a decision that meant "no unpinned network": a download whose target digest is a constant in the source, verified before load, is the discipline `Udpipe::english` has had since 0.1.0, and it now covers the reference embedding model. Caller-supplied files stay a first-class path; the constructor a caller reaches for is what decides whether provisioning happens.
- The `just conformance` semantic lane no longer needs a hand-placed model. Both Rust and Python runners obtain potion-base-8M through the pinned-download constructor into the resolved directory, and `MATRA_MODEL2VEC_DIR` still names that directory when it is set. The lane stays behind `--ignored` and the `model` marker, because the first run needs a network.
- **The `--json` payload is now an envelope.** Every command emits one object: `{"format_version": 1, "command": ..., "input": ..., "result": ...}`, where `result` is the serde form of the domain value, unchanged. This is a deliberate change to what the 0.1.0 command line printed. It is not a break of a single contract, because there was no single contract: the Rust binary and the Python CLI each emitted their own JSON. The envelope buys two things a bare payload cannot. A consumer can tell which command produced a document and which input it read without being told out of band, and `format_version` gives the payload a stability statement it did not have. The precedent is cargo's, which extends "stable and versioned" to `cargo metadata --format-version` and to nothing else; matra makes the same narrow promise. `format_version` increments on any change to the envelope or to the meaning of a field inside `result`.
- The Python package's `matra` command is the Rust CLI, reached through the extension module. `python/matra/cli.py` re-implemented argument parsing and rendering in click and rich, and had drifted: it carried a `--sections` flag the Rust binary lacked, ignored `--model-dir` and `MATRA_MODEL_DIR`, detected only `.md` as markdown, fed unstripped markdown to the extractors, and used a different exit-code convention. All of that is gone, along with the class of defect that produced it (ADR-0011).
- The `python` feature enables `cli`, so a wheel carries the command line. `clap` and `clap_complete` are compiled into it.
- `matra summarize` and `matra keyphrases` take their default count and algorithm from the config file's `summarize` and `keyphrases` sections when the flags are absent. The shipped defaults are the ones the flags used before, so nothing changes for a user with no config file.
- The docsite floor's type-name gate and its em-dash gate now cover `skills/` as well as `book/src/`, so the agent skill is held to the same two rules the docsite is. The em-dash gate also matches an em dash for the first time: its pattern was written as an escape that grep reads as the letter u followed by `2014`, so the gate had never fired. Nothing in the tree was hiding behind it.
- Docsite: an Explanation section (concepts, situation model, programming model, pragmatics) now precedes the guides; the capabilities page is a straight per-tier reference; architecture and boundary rules move under Contributing. Existing pages lose meta-commentary and restatement without losing facts. The domain-model page now records `passive_ratio` as a stored field that crosses to Python, which it has been since 0.1.0.

### Removed

## [0.1.0] - 2026-08-21

First release. The surface this version freezes is the one pipeline
(ADR-0007) plus the five structural primitives (ADR-0008): everything
below happened pre-publish, which is why none of it carries a
deprecation.

### Highlights

**One pipeline replaced six entry points.** The old surface enumerated its calling conventions: `analyze`, `analyze_markdown`, `analyze_file`, `analyze_directory`, `parse`, and `analyze_from` were partial applications of one chain, and each restated invariants the compiler checked in none of them. Two live defects had that exact shape: the input size cap was bypassable from Python because four methods restated it and four did not, and `analyze_from` returned a half-populated `Document` because the metric suite carried the sentence set twice. The surface is now `Ingest` (a string is a stream of one, a directory is a stream of many) into `Engine` (`analyze`, or the stages `annotate` and `compose`). `annotate` is the only route from text to the parser, so the size cap is a property of the pipeline rather than of each entry point, and seven equivalence laws in the test suite pin the grains together. Streams are lazy: a directory holds one document's allocations at a time, and per-file failures travel as `DocumentError` items instead of aborting the walk.

**Structural primitives cross FFI as fields.** Five rule-substrate primitives landed: negation cues, modal auxiliaries with the bare-assertion discriminator, reporting constructions and root adverbials for evidentiality, and the six Hearst hypernymy patterns as span pairs. The question they forced, whether a derived structural fact is a method or a field, is settled by ADR-0008: a derivation is computed once in Rust at a pipeline choke point and crosses every FFI boundary as serialized data, while views over data already crossing (ADR-0009's `Token::feat` lookup) stay Rust-only methods. Before this, the Python CLI re-implemented passive detection against a parse Rust had already read; that duplication is deleted, and `spec/tests/` fixtures now pin each crossing primitive across crusts. Every primitive reports structure (the cue, the arc, the construction, the span pair) and leaves interpretation to the consumer, which is the substrate line the rule vocabulary will be designed against.

**The project is now called matra.** The previous name collided with an existing package on PyPI, which makes dual publishing to crates.io and PyPI under one name impossible. The name is the public contract across Rust, Python and a future TypeScript crust, so the collision had to be resolved before the first release rather than after. There are no consumers and nothing has been published, so the change carries no aliases, shims or deprecations.

**A command-line interface ships behind the `cli` feature.** The library returns typed errors and structured data; the binary decides rendering, exit codes, and what to do when input is missing. Exit codes follow the ripgrep convention, so nothing-found is 1 and a genuine failure is 2, and an empty document is not an error. `summarize` and `keyphrases` route through the same format detection `analyze` uses, so markdown headings and fenced code are never ranked as prose.

**Conformance fixtures now bind the crusts together.** matra ships one Rust core behind several bindings that all call the same parser, so a difference between them is never a difference of behaviour: it is a binding defect, a renamed field or a value that lost precision crossing over. `spec/tests/*.json` holds language-agnostic fixtures with one runner per language. The UDPipe model is part of the contract, so a model version change is a spec change.

### Added

- `Ingest`, `Engine`, `standard_decomposers`, `decompose::Decomposers`: the pipeline surface.
- `domain::DocumentError` (per-document failure with its path) and `domain::CorpusResult` (the partition of a result stream, constructed by `collect()`).
- `Format` derives `PartialEq` and `Eq`, which the decomposer table keys on.
- Equivalence laws L1 to L7 as tests: chain homomorphism, empty, singleton injection, stage composition, partition, Err passthrough, and the size-cap bound on everything the parser sees.
- `matra` binary behind the `cli` feature: `analyze`, `summarize`, `keyphrases`, each accepting `--json`.
- Conformance suite: `spec/tests/*.json` with Rust and Python runners.
- `tests/cli.rs` covering argument handling, format detection, output shape and exit codes.
- `rust-toolchain.toml` pinning stable. The MSRV claim is verified separately by CI.
- `ROADMAP.md`, the single register of unbuilt capability and its trigger conditions, rendered into the book.
- `book/src/plans/`, the iteration plans, with per-milestone rubrics.
- Docsite floor gate 5: no em dashes outside quoted material.
- `domain::Negation` and `Sentence.negations`: negation cues (`not`, `never`, `no`, `neither`, `nor`) detected from the dependency graph at sentence construction and serialized with the sentence, so every crust reads one Rust detection (ADR-0008).
- `Document.passive_ratio` as an `Option<f64>` slot filled by the metric suite, beside `vocabulary_ttr` and `nominalization_ratio`; the aggregate now crosses FFI as data, and the Python CLI reads it instead of re-deriving passive detection from raw tokens.
- ADR-0008: derived structural facts cross FFI as serde-visible fields with a single Rust implementation; zero-information accessors over data already on the wire stay Rust-only methods.
- Conformance fixture `spec/tests/negation.json` pinning per-sentence negation cues and `passive_ratio` across crusts.
- `domain::Modal` and `Sentence.modals`: modal auxiliaries detected at sentence construction and serialized with the sentence (ADR-0008 mechanism). The closed class is the ten UD English `MD` lemmas (`can`, `could`, `may`, `might`, `must`, `ought`, `shall`, `should`, `will`, `would`), matched by lemma on the `aux` relation or the `AUX` part of speech, which catches modals the model promotes to root or `conj` under VP ellipsis and coordination; the epistemic, deontic or dynamic reading stays with the consumer.
- `Sentence.bare_assertion`: the bare-assertion discriminator, true when the root clause is finite indicative (`Mood=Ind` on the root or on a `cop`/`aux`/`aux:pass` child of it, covering copular, do-support and passive clauses) and no modal auxiliary governs it. Reads the root clause via `Token::feat`.
- Conformance fixtures `spec/tests/modal.json` and `spec/tests/modal-coordination.json` pinning per-sentence modals and the bare-assertion discriminator across crusts, including VP ellipsis, coordinated auxiliaries and the copular bare assertion.
- `domain::Reporting` and `Sentence.reportings`: reporting constructions detected at sentence construction and serialized with the sentence (ADR-0008 mechanism). The construction is structural (a verb governing a `ccomp`, plus its `nsubj` when the sentence has one) and fires for every verb that fills it: reporting verbs are an open class, so matra ships no lexicon and `Sentence::reportings_in` takes the caller's as a parameter. The subject is optional because UDPipe splits "Smith et al. reported ..." at the period in "et al.", stranding the attribution in the previous sentence; the upstream defect is recorded in the test suite, not fixed here.
- `domain::RootAdverbial` and `Sentence.root_adverbials`: adverbial modifiers attached to the root, the arc sentence-scope adverbs ("Reportedly, ...") land on, detected at sentence construction and serialized with the sentence. The parse does not distinguish sentence scope from manner, so every root-attached `advmod` is reported and `Sentence::root_adverbials_in` filters by the caller-supplied lexicon; which lemmas read as evidential stays the consumer's call.
- Conformance fixture `spec/tests/evidentiality.json` pinning per-sentence reporting constructions and root adverbials across crusts: self-attribution ("We show that"), other-attribution ("Smith reported that"), impersonal ("These results suggest that"), and the hearsay adverb ("Reportedly, ...").
- `hearst` module, `domain::HearstPair`, `domain::HearstSpan`, `domain::HearstPattern`, and `Sentence.hearst_pairs`: the six Hearst (1992) hypernymy patterns (`NP such as NP`, `such NP as NP`, `NP, including NP`, `NP, especially NP`, `NP and other NP`, `NP or other NP`) detected as dependency-arc patterns over the parse, not regex over surface text. Each pair carries the pattern tag plus hypernym and hyponym spans referencing token ids, so provenance holds. Precision over recall: each detector requires the full arc shape verified against live parses, so clausal coordination, definite contrastive coordination ("the teacher and the other students"), and emphasized plain coordination do not fire and misparses are missed rather than misreported. The detector lives outside the domain and the pipeline fills the field at the annotate stage; the pair is a candidate, not an asserted taxonomy edge.
- Conformance fixture `spec/tests/hearst.json` pinning Hearst pairs across crusts: the `such_as` and `and_other` patterns plus a clausal-coordination hard negative pinned to an empty result.
- `Token::feat`: borrowed lookup of one morphological feature in the CoNLL-U `feats` string, first exact-key match, no allocation. Rust-only by design since `feats` already crosses FFI as a string (ADR-0009).
- ADR-0009: feats access is a lookup accessor, not an exhaustive enum and not a per-token map; derivations cross as fields, views over crossing data stay methods.

- The six entry points: `analyze`, `analyze_markdown`, `analyze_file`, `analyze_directory`, `analyze_from`, `parse`. Variation lives in `Ingest`'s constructors and the decomposer table, not the function namespace. Pre-publish, so no consumer breaks.
- `Metric`'s sentence-slice parameter. Metrics read the one sentence set attached to the document's paragraphs, which removes the redundant representation behind the `analyze_from` half-population defect.
