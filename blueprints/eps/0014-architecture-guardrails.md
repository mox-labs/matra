# EP-0014: Architecture guardrails: the boundary rules as semgrep checks

- EP: EP-0014
- Implements: none (standalone: this changes how matra is checked, not matra)
- Status: planned
- Shipped in: not shipped (CI and harness; no crate release carries it)

## Summary

Seven of the eight boundary rules in
`site/content/reference/boundary-rules.md` become mechanical checks, written
as semgrep rules in `.semgrep/`, each tested against a fixture of the forms
it claims to catch, and run by `scripts/check-boundaries.sh` from
`just check`, the pre-commit hook and the `Boundary check` CI job. Each
finding's message states the rule, what was violated, why the boundary
exists, and the section of `boundary-rules.md` to read, so the check teaches
whoever trips it. This is the bottom layer of a larger restructure: nothing
moves until the boundaries hold mechanically.

## Design

### The problem

Before this plan, rule 6 was compiled, rules 3, 4 and 8 were a ripgrep over
the literal `use crate::<port>` and `use udpipe_rs` forms, and rules 1, 2, 5
and 7 were review only. The grep missed brace groups, inline qualified
paths, re-exports and trait bounds, and `boundary-rules.md` listed those
blind spots. A restructure that moves files is exactly when a boundary slips,
and review is the gate most likely to be tired then.

### The rule-to-check table

Every rule id below is in `.semgrep/`, and every one has at least one
`ruleid:` and one `ok:` case in its fixture, which the check itself enforces.

The rule 1 question the old docs raised, whether a dependency added to
`Cargo.toml` and used in `src/domain.rs` is caught: it now is, whenever
`domain.rs` names it, by a `use` line or an inline path. The one route left is
a macro or derive made available crate-wide by `#[macro_use]` in
`src/lib.rs` and invoked unqualified.

### Why regex rules, and how they are built

Semgrep's Rust AST patterns were measured on semgrep 1.157.0 against the
forms these rules must catch, and they fail silently in exactly the places
that matter: `use crate::nlp::$X;` misses brace groups; `crate::nlp::$X`
matches a two-segment call but not a three-segment path or a type position;
the path ellipsis `$...X` matches nothing; `extern crate $X;` matches every
`use` line. Worse, a `languages: [rust]` rule skips any file the Rust parser
rejects, with only a warning. So every rule is `languages: [regex]`, which
reads every byte of every file in its `paths`. Four construction choices
follow, each from a measured failure:

- **Allowlists are negative lookaheads inside the regex.** A
  `metavariable-regex` filter rejects the first candidate on a line and does
  not backtrack to the next, so `{domain::A, domain::B, nlp::C}` slipped.
- **Comment lines are skipped by the positive regex**, via
  `(?m)^(?![ \t]*//)[^\n]*?\K`. A `pattern-not-regex` for comments is wrong:
  semgrep drops every finding that merely overlaps an excluded range, so a
  comment line inside a multi-line brace group hid the whole group.
- **`pattern-not-regex` is used only for ranges a finding sits wholly
  inside**: `#[cfg(test)] mod` blocks, matched with balanced braces that skip
  braces in strings, raw strings, chars and comments (a string continuation
  line broke the first version); and whole `use` statements for the
  inline-path rules, matched on path characters only so that a string
  starting "use the" cannot swallow the code after it.
- **Brace groups are read item by item**, with comments as atomic tokens, so
  a comma in a comment is not an item separator.

### Why the wrapper, not a bare `semgrep` call

`scripts/check-boundaries.sh` runs `semgrep --test` on each rule file and its
fixture, then `semgrep scan --config .semgrep --error src`, and adds three
guards, each against a measured silent pass:

- Semgrep's test discovery skips a dot-directory: `semgrep --test .semgrep`
  reports "No unit tests found" and exits 0. The script pairs each
  `.semgrep/NAME.yml` with `.semgrep/NAME.rs` explicitly and fails if a rule
  id has no `ruleid:` or no `ok:` case.
- Outside a git work tree, every rule with `paths:` matched nothing and bare
  semgrep exited 0 over a planted violation. The script refuses to run
  anywhere but the root of a work tree.
- Semgrep's default ignore list skips any `test/` or `tests/` directory, and
  files over 1 MB are skipped by default. `.semgrepignore` exists to replace
  the default list (it ignores nothing), the scan passes
  `--max-target-bytes=0 --timeout=0`, and the script fails unless the scan
  read every Rust file under `src/` with no semgrep error.

`semgrep --test` ignores `paths:`, so fixtures run every rule in their file;
that is why fixtures are one per rule file, and why scoping was proven
separately (see the test plan).

### How to add a rule

1. Put the rule in the `.semgrep/` file for its boundary rule, or a new
   `.semgrep/NAME.yml`, with `languages: [regex]`, `paths:` for its scope,
   and the line-anchored, `\K`, lookahead construction described at the top
   of `.semgrep/rule1-domain.yml`.
2. Write the message for a reader who has never seen the repo: the rule
   number, what was violated, why the boundary exists in one sentence from
   `boundary-rules.md`, the fix, and the section to read.
3. In `.semgrep/NAME.rs`, add a `// ruleid: <id>` case for every syntactic
   form the rule claims (plain `use`, nested path, brace group, multi-line
   group with a comment, inline path, `pub use`) and at least one
   `// ok: <id>`. Run `just boundary`; it fails until both exist.
4. Plant a violation in the real file the rule scopes to and watch
   `just boundary` fail, then revert it. `semgrep --test` cannot prove the
   `paths:` scoping.
5. Update the table in `boundary-rules.md` and this table.

### What stays review-only, and why

Review remains the gate for what an import cannot show: whether a trait's
shape leaks an adapter (rule 2), whether a function takes text where it
should take structure (rule 5), and whether a file other than `src/lib.rs`
wires adapters together (rule 7 beyond the CLI). These are judgments about
meaning, and a pattern that tried to encode them would either flag correct
code or be tuned until it flagged nothing. The laundering routes in the table
are left to review because each is rare, and catching them in general needs
name resolution, which a regex does not have.

### The pin

Semgrep and its 66 transitive dependencies are pinned by version and hash in
`.github/requirements/semgrep.txt`, resolved universally so that macOS and
Linux install from the same file, and installed with
`pip install --require-hashes`. That is the pip analog of the SHA-256-checked
release assets the other CI tools use. The script prints a note when the
local semgrep differs from the pin; the rule tests decide whether the
difference matters.

## Goals

- Rules 1, 2, 3, 4, 5, 7 (its CLI part) and 8 fail `just check`, the
  pre-commit hook and the `Boundary check` job on every form in the table.
- Every rule is tested against fixtures, and a rule without a `ruleid:` and
  an `ok:` case fails the check.
- A scan that read less than all of `src/` fails.
- `CLAUDE.md`, `boundary-rules.md` and the skills say which rules are
  mechanical and which are review, truthfully.

## Non-goals

- Moving any code. The restructure this protects comes after it.
- Rules for adapter-to-adapter imports or the rest of rule 7, which need a
  decision about what an adapter may import before they can be checked.
- Replacing review. The checks catch forms; review reads intent.

## Iterations and milestones

### M1: the rules, the check, the wiring

- **Deliverable.** `.semgrep/` with seven rule files and their fixtures,
  `.semgrepignore`, `.github/requirements/semgrep.txt`,
  `scripts/check-boundaries.sh` rewritten around semgrep (the ripgrep checks
  retired), the `Boundary check` job installing the pinned semgrep, the
  pre-commit hook running the check when semgrep is present (the scan alone,
  `--scan-only`, about 3 seconds, unless a rule, fixture or the script is
  staged; the full run with rule tests takes about 70), and the
  enforcement text in `CLAUDE.md`, `boundary-rules.md`, `AGENTS.md`,
  `CONTRIBUTING.md` and the agent and skill files brought in line.
- **Exit criterion.** `just check` passes; every rule fires on its fixture;
  a violation planted in the real file each rule scopes to fails the check,
  and allowed code planted in the same places does not.

## Test plan

- `semgrep --test` per rule file, from the script, on every run except the
  pre-commit hook's `--scan-only` run when no rule, fixture or script is
  staged.
- Planted violations on a throwaway git copy of the real tree, one per rule,
  at the rule's real path: each must produce that rule's finding at the
  planted line. Negative controls (`udpipe_rs` in its adapter, an adapter
  import in `src/lib.rs`, a string error in `src/cli/`, a sibling `super::`
  in extraction) must produce none. A module under `src/nlp/tests/` must be
  read. Outside a git work tree the script must refuse.
- The CI install path (`pip install --require-hashes` on Python 3.12,
  linux/amd64) run in a container before the pull request.

## Ship criteria

M1's exit criterion holds on `main`, and the `Boundary check` job passes
there with the pinned semgrep.

## Risks

- **A new semgrep reads a regex differently.** Signal: a rule test fails
  after the pin moves. Response: the fixtures are the contract; fix the
  rule, not the fixture.
- **A false positive in a string or a block comment.** Regex rules see text,
  not tokens. The failure is loud (a finding), not silent; the response is a
  narrower regex with a fixture case, never an exclusion broad enough to
  hide code.
- **A test module the exclusion cannot balance** (an unusual literal). The
  exclusion then does not apply and the module's test code is read as
  library code: loud. The reverse, an exclusion running past the end of a
  test module, needs a literal the tokenizer misreads; the raw-string case
  that could do that is handled and pinned by a fixture. Clippy does not
  forbid items after a test module (measured: `items_after_test_module` did
  not fire under `-D warnings`), so this is not backstopped.
