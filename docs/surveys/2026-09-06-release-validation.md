# Release validation survey, 2026-09-06

A read-only survey run ahead of matra's first public release, to ground the design of a durable, agent-run release-validation methodology (a documented process, a reusable sandbox, and an agent that executes it before each release). No code changed as part of this survey. Every citation is a URL fetched this session or a repository file path read this session. Absences were established by reading the actual workflow files and checklists, not by memory. Nothing below is a recommendation; the "What this implies for matra" section at the end is the only place judgment appears, and it is kept separate from the findings.

Two questions were asked. Question 1: what is the named, established methodology for validating a released artifact from a user's point of view. Question 2: what do real open-source projects that ship a Rust core with a Python wheel, or a Rust CLI binary, actually do. The two answers turned out to diverge sharply, and that divergence is the main finding.

## 1. Named methodologies

### Session-Based Test Management (SBTM) and exploratory testing charters

SBTM structures exploratory testing around a "session": an uninterrupted, chartered block of test effort, roughly 90 minutes (Jonathan Bach and James Bach suggest "short" at about 45 minutes and "long" at about 2 hours). A session is scoped by a charter (a mission statement plus the areas to be tested, tagged with `#AREAS` keywords) and reported afterward on a **session sheet**. The session sheet's sections, per the original source: session charter, tester name(s), start date and time, a task-breakdown metric (percentage of time on Test Design and Execution / Bug Investigation and Reporting / Session Setup, plus duration and the ratio of on-charter to off-charter exploration), data files, test notes, issues, and bugs. A companion debriefing uses the mnemonic PROOF (Past, Results, Obstacles, Outlook, Feelings) as the reviewing manager's agenda.

Origin: Jonathan Bach and James Bach, based on a process piloted at Hewlett-Packard, published as "Session-Based Test Management" in *Software Testing & Quality Engineering* magazine, Nov/Dec 2000. Primary source: https://www.satisfice.com/download/session-based-test-management (the original article, fetched and read this session). Corroborated by https://en.wikipedia.org/wiki/Session-based_testing.

Deliverable: the session sheet itself, plus aggregated tables (test notes, bugs, issues, charters, coverage, tester, and per-day breakdowns) generated by scanning a repository of session sheets.

Gate or judgment: **explicitly a judgment artifact, not an automated gate.** The source states the session report is meant to be "examined by a third-party, such as the test manager," followed by a mandatory human debriefing whose stated objective is "to understand and accept the session report." The one piece of tooling described (a Perl scanner) performs mechanical consistency checks, such as verifying that referenced data files exist, and produces summary tables; it does not adjudicate whether the testing was adequate. The article itself warns its own numbers "could easily be distorted by a confused or biased test manager," which is the source underscoring, not disclaiming, that judgment is where the method places its weight.

### Defect report quality standard: RIMGEN (corrected from the assumed RIMGEA/Bach attribution)

The task's premise named RIMGEA and attributed it to James Bach or Michael Bolton. That attribution does not hold up against the sources. Four independent sources agree the mnemonic originates with **Cem Kaner** (with Rebecca Fiedler), taught in the BBST (Black Box Software Testing) "Bug Advocacy" course: https://bbst.courses/rimgen/, https://bbst.courses/bbst-bug-advocacy/, https://www.kenst.com/how-to-write-a-good-bug-report-use-rimgen/, http://prairietester.blogspot.com/2013/09/rimgea-bug-reporting-heuristic.html. The mnemonic has two documented forms, an older RIMGEA and a revised RIMGEN; Kaner's own 2002 Quality Week deck (https://kaner.com/pdfs/BugAdvocacy.pdf, fetched and read) covers the underlying practices at length (for example "REPLICATE EVERY BUG ON A SECOND MACHINE") but the literal acronym does not appear verbatim in that specific 2002 artifact, so treat the acronym as a teaching mnemonic distilled from the course rather than coined in that exact document.

What it prescribes, current (RIMGEN) form: Replicate (reproduce the bug, ideally on a second machine or configuration), Isolate (cut the reproduction to the minimal necessary steps, one failure per report), Maximize (follow-up testing to check for a more severe underlying bug), Generalize (check whether the bug recurs more broadly, other data, other platforms, related areas), Externalize (reframe from "the program failed" to who is affected and how, the business or user impact), Neutral tone (objective, dispassionate language, no editorializing; the older RIMGEA form ends instead on "And say it clearly and dispassionately").

Deliverable: a single bug report, written to be reproducible, minimized, investigated for severity and scope, and framed for the reader who has to act on it.

Gate or judgment: **a human-authored and human-reviewed quality heuristic, not a machine check.** Kaner's course material describes a second tester reviewing a report for clarity and reproducibility before it reaches a programmer. No source describes RIMGEN as machine-checked; it is a checklist for a person writing or editing prose.

### User Acceptance Testing as distinct from System Testing

Per the ISTQB glossary (fetched via a mirror, https://istqb-glossary.page/user-acceptance-testing/ and https://istqb-glossary.page/system-testing/, since a direct fetch of the primary glossary.istqb.org domain returned no content, likely because it is client-rendered; this is a caveat on primary-source access, not on the wording, which the mirror attributes to the official ISTQB glossary and matches well-known ISTQB phrasing): User Acceptance Testing is "acceptance testing carried out by future users in a (simulated) operational environment focusing on user requirements and needs," cited to the ISTQB Advanced Test Analyst 2012, Advanced Technical Test Analyst 2012, and Foundation Extension Agile Tester 2014 syllabi. System Testing is "testing an integrated system to verify that it meets specified requirements," cited to the ISTQB Foundation 2018 syllabus.

The distinction the glossary draws: system testing verifies conformance to documented specifications, typically run by a test team. UAT is defined by who performs it: future users (or business stakeholders) judging real-world fitness for their own needs, not technical conformance to a written spec. Both are named test levels, run sequentially, in the ISTQB model. No ISO/IEC/IEEE 29119 primary text was reached this session to corroborate independently; 29119-1 is understood to define acceptance testing as a level, but that wording was not verified against the standard itself here.

Gate or judgment: **both are human-run test levels, not tooling categories**, but UAT is more explicitly a judgment activity by its own definition: it is future users deciding acceptance, not a specification check that could in principle be automated.

### Documentation as tests / literate and executable documentation

This is the one category in the survey that is unambiguously automated. Four tools were verified directly against primary documentation, each extracting code from documentation and running it with an exact pass/fail comparison:

- **Rust doctests** (`cargo test --doc`), https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html. Rustdoc extracts fenced code blocks from `///` doc comments, wraps each in a runnable harness, compiles it as its own test binary, and runs it; `should_panic`, `no_run`, `compile_fail`, and `ignore` attributes modulate the expected outcome. Fully automated pass/fail, wired into `cargo test`.
- **Python `doctest`**, https://docs.python.org/3/library/doctest.html. States its own purpose as searching docstrings for text that looks like an interactive session and executing it "to verify that they work exactly as shown," with exact string comparison of captured output against the text written in the docstring.
- **`pytest --doctest-modules`**, https://docs.pytest.org/en/stable/how-to/doctest.html. Runs the same doctest-format examples through pytest's collection and execution machinery, adding pytest's diff reporting on mismatch.
- **Sphinx's `doctest` extension**, https://www.sphinx-doc.org/en/master/usage/extensions/doctest.html. Collects marked-up code and expected-output blocks per document, groups them with optional setup blocks, and runs them via a dedicated `doctest` Sphinx build target (`sphinx-build -b doctest`).

A fifth item, Cucumber/Gherkin, was checked at a shallower level (https://cucumber.io/docs/bdd/better-gherkin/, https://cucumber.io/docs/gherkin/reference/): Gherkin scenarios are simultaneously the human-readable spec and the literal input to automated step-definition execution, which Cucumber's own docs describe as functioning as "living documentation." README-specific tools named in the task (`mdsh`, `markdown-doctest`, `doctest-rs`, `runmd`, `cram`, `sybil`) were not independently checked this session; they should be treated as unverified rather than assumed equivalent.

Gate or judgment: **automated pass/fail**, uniformly, across every tool confirmed. This category is the exception to the pattern in the rest of Question 1: it is gate-shaped, not report-shaped.

### Clean-room, hermetic, and install-matrix testing

No single named methodology was found for this, unlike SBTM or RIMGEN. It is common practice, implemented by several independently documented tools rather than one named discipline:

- **cibuildwheel**, https://cibuildwheel.pypa.io/en/stable/. States its purpose as running "your library's tests against the wheel-installed version of your library" in isolated environments across "Mac, Linux, Windows, on multiple versions of Python," configured via `before-test` and `test-command`.
- **tox**, https://tox.wiki/en/latest/. Describes itself as "checking your package builds and installs correctly under different environments," acting as a CI/CD frontend; it is a tool that automates the already-existing practice, not a named methodology of its own.
- **nox**, the Python-code-configured equivalent of tox, same practice, different configuration style (checked via search results, not a direct primary-doc fetch this session).
- **GitHub Actions matrix strategy**, https://docs.github.com/en/actions/using-jobs/using-a-build-matrix-for-your-jobs. Automatically creates one job run per combination of matrix variables (for example three OSes by three language versions equals nine jobs), with `fail-fast` and `continue-on-error` controlling how failures aggregate.
- The Python Packaging Authority's general guidance (packaging.python.org) documents venv and virtualenv as the standard isolation mechanism for installs, but no single PyPA page prescribing "install-matrix testing" as a named practice was found; treat that link as general context, not a citable methodology page.

Gate or judgment: **automated pass/fail**, uniformly. Every tool confirmed here either passes or fails a build; the only human judgment involved is a design-time decision about which combinations belong in the matrix, not judgment on the result.

### Time-to-hello-world as a first-run developer-experience metric

**Nothing rigorous was found.** The phrase appears repeatedly in vendor and blog content, for example Fern's blog on reducing time-to-hello-world for enterprise partners (https://buildwithfern.com/post/reduce-time-to-hello-world-enterprise-partners, dated July 2026), and Moesif/Nordic APIs material using "Time to First Hello World" and "Time to First Call" as informal API-onboarding concepts, none of which state a measurement protocol or a validation study. The DORA metrics in *Accelerate* (Forsgren, Humble, Kim) do not include it: the four DORA metrics are Deployment Frequency, Lead Time for Changes, Mean Time to Recovery, and Change Failure Rate, confirmed via multiple secondary summaries; no onboarding-time metric appears among them.

The one rigorous, peer-reviewed metric found in the same problem space measures something adjacent but different: Abi Noda's DX newsletter (https://newsletter.getdx.com/p/developer-onboarding-time) cites a Google study, "Onboarding and Ramp-Up" by Collin Green and Ciera Jaspan (IEEE Xplore), which validates two proxy metrics for engineer ramp-up, normalized active coding time per line of code and normalized submitted lines of code, and explicitly warns both are "highly erratic and noisy" at the individual level, useful only for comparing training programs across groups, never for judging an individual. This is a legitimate citation for ramp-up measurement in general, but it is not a citation for time-to-hello-world specifically, and the two constructs should not be conflated.

Gate or judgment: not applicable as a testing gate at all; where it is used, time-to-hello-world is a product-analytics or UX metric reported to humans for a decision, not a release gate in any source found.

### crate-ci/cargo-release

Not a project shipping its own release, but a tool that automates the release process for other Rust crates, and it is the one item in the survey with built-in verification logic rather than a checklist file. Per `docs/reference.md`:

- Dry-run is the default: nothing is pushed, published, or tagged unless `-x`/`--execute` is passed.
- A `verify` config key (default true, disabled with `--no-verify`) builds the packaged crate as a pre-publish check; a `target` key lets that verification build target a specific triple.
- A `pre-release-hook` config key runs an arbitrary command before the version-change commit, aborting the release if it exits non-zero, with `PREV_VERSION`, `NEW_VERSION`, `DRY_RUN`, `CRATE_NAME`, `WORKSPACE_ROOT`, `CRATE_ROOT` exposed as environment variables. This is the tool's extension point for a caller to plug in their own smoke test.
- The tool documents no separate human checklist; instead, `docs/reference.md` describes the pipeline of steps (changes, version, replace, hook, commit, publish, owner, tag, push, drawn from the tool's own `--help` output) as the checklist, codified as the tool's step sequence rather than a prose document.

Citation: `docs/reference.md`.

## What this implies for matra

Two things generalize cleanly across all nine repositories: every one of them, without exception, treats "does the built artifact install and run" as fully automated CI, never as a step a human is asked to judge. And every one of them keeps that automated check separate from whatever human-triggered release process exists (version bump, tag, changelog, publish approval), which is documented as a checklist in a plain file (bat's `doc/release-checklist.md`, ripgrep's `RELEASE-CHECKLIST.md`, uv's and ruff's `CONTRIBUTING.md` sections) only for the pure-Rust-binary and Rust-core-with-thin-Python-wheel projects, and is largely absent or weak for the two projects closest to matra's actual shape, `polars` (a policy on cadence, not a checklist, and its Rust-crate release path is currently disabled) and `pydantic-core` (no checklist at all, only a mechanical version-tag check). matra cannot copy a release checklist from its two nearest analogues; it would have to write one in the style of bat or ripgrep instead.

Executing documentation as an automated test is real and cheap where the language gives it for free: Rust's `cargo test --doc` needs no additional tooling matra doesn't already have, and matra's own doctests already run under `cargo test`. Extending the same discipline to the Python surface, the way polars (`run_doctest.py`, `test_user_guide.py`) and pydantic-core (`test_docstrings.py` against both docstrings and `README.md`) do, is not something matra has built yet and is a gap this survey identifies concretely, not a recommendation to build it, since whether it is worth the maintenance cost for a library at matra's current scale is not something this survey measured.

The named human-judgment methodologies from Question 1, SBTM, RIMGEN, and formal UAT, do not appear anywhere in the nine release pipelines read for Question 2. None of the nine repositories shows evidence of chartered exploratory sessions, RIMGEN-formatted bug reports, or a formal user-acceptance step as part of release engineering. What real Rust-core, Python-wheel, and Rust-CLI projects substitute for that layer is entirely mechanical: matrix builds, install-then-run smoke tests inside containers, and a prose checklist for the parts that cannot be mechanized (deciding the version number, writing the changelog, approving the deploy). This is the sharpest finding in the survey: the established, citable, human-judgment testing methodologies exist in the testing literature, but they are not what the closest real-world analogues to matra actually run before a release.

What the evidence does not settle: whether matra's agent-run methodology should be built entirely in the automated-gate style that every surveyed project actually uses, or should also incorporate a judgment-producing layer, such as a session-style exploratory pass or a UAT-style acceptance step, that no surveyed project integrates into release engineering even though the methodology exists and is well documented. It also does not settle whether a container-based clean-room smoke test earns its complexity at matra's current size, a single crate with one CLI and one Python wheel, versus the multi-target, multi-architecture scale of uv, ruff, or polars, since no cost or failure-rate data was gathered on that question. Both are design decisions for whoever specifies the methodology next, not conclusions this survey can draw from what nine repositories happen to do.
