# 0018. The Docsite on SvelteKit: Plain Markdown, Figures From matra's Own Output

- **Status:** proposed
- **Date:** 2026-09-23
- **Decider(s):** owner direction (move the docsite to Svelte for interactive,
  explorable explanations and data graphics); evidence, options and
  constraints by the maintainer role

## Context

The docsite is an mdBook of 26 pages under `book/src/`. It is accurate and
guarded: six gates in `scripts/check-docsite-floor.sh` run in CI, two tests
(`tests/cited_figures.rs`, `tests/error_tables.rs`) pin pages to the code and
to measured figures, and `book/src/llms.txt` is generated from `SUMMARY.md` so
an agent can find every page.

What it cannot do is show matra's output the way the output is shaped. A
dependency parse is a tree with arcs between words. Metrics are distributions
across paragraphs and sections. Semantic clusters are a similarity space. Today
those appear as seven hand-drawn SVGs and a number of tables. The owner wants
the docsite to carry explorable figures and data graphics, to help people take
matra up.

Constraints that any design has to meet:

1. **Parsing does not run in the browser.** UDPipe is C++ behind an FFI panic
   boundary. The rest of the crate checks on `wasm32`, the parser does not. A
   figure cannot parse the reader's text live.
2. **The docs describe what ships.** Every figure must show real output of the
   released library, never an illustration of what it might produce.
3. **Agents read these docs.** matra is used by agents as much as by people.
   Agents do not see a rendered, animated figure: vision APIs take the first
   frame of an animation, and a d3 figure is not text. Whatever a figure shows
   has to exist as text too.
4. **The gates must survive the move.** A migration that drops a gate loses
   protection silently, which is the failure class ADR-0017 exists to remove.
5. **Published URLs are cited elsewhere.** `Cargo.toml` `homepage`,
   `CITATION.cff`, `README.md`, `scripts/gen-llms-txt.sh` and the generated
   `llms.txt` all name `https://mox-labs.github.io/matra/<path>.html`.

What the evidence says about figures and motion, in brief (references below):

- Animated transitions between two states of the same graphic improve
  comprehension of the change, with careful design (Heer and Robertson 2007).
  Staging beyond about two steps increases error in the same study.
- Motion near text draws attention away from the text. A self-starting
  animation that lasts over five seconds needs a pause control at WCAG
  Level A (2.2.2). No controlled evidence was found that ambient or decorative
  motion improves comprehension, recall or engagement.
- Diagrams help readers who already know how to read them. An unfamiliar
  encoding, such as a dependency tree for someone new to syntax, costs a novice
  more than a table does.
- Asking the reader to predict before revealing the answer helps novices and
  stops helping, or starts to hurt, as expertise grows (expertise reversal).
- Readers follow information scent and leave when it runs out. Overview first,
  with a stable layout, is supported. Interaction is worth its cost only when
  it lets the reader ask a question the static page could not answer
  (Victor, *Magic Ink*).

## Options considered

### Option A: stay on mdBook, add figures as embedded HTML and JS

Keep `book/`, and add interactive figures as `<script>` islands in pages.

**Pros:** no migration; every gate stays as it is.
**Cons:** mdBook has no component model, so every figure is hand-wired JS with
no shared layout, no prerendering and no types. Figures would be the least
maintained part of the site. It does not meet the owner's direction.

### Option B: SvelteKit with mdsvex

Pages become `.svx` files that mix Markdown and Svelte components.

**Pros:** the common SvelteKit route; components sit inline in prose.
**Cons:** the page source stops being Markdown. `llms.txt`, gates 2, 3 and 5,
`tests/error_tables.rs` and any agent reading the repository would have to
parse Svelte syntax, or would quietly stop seeing the parts that live in
components. It ties the content to one preprocessor.

### Option C: SvelteKit, plain Markdown, named tags for figures

Pages stay plain Markdown files. A figure is a single self-closing tag in the
Markdown, such as `<figure-parse sentence="concepts-1" />`. The build renders
Markdown with a remark/rehype pipeline and maps each known tag to a Svelte
component. Figure data is matra's own output, generated by a Rust example at
docs build time and committed as JSON.

**Pros:** the source stays readable as Markdown by every existing gate, test
and agent. A figure in the source is one line naming its data, so the data is
where the meaning lives. Prerendering puts the full figure in the static HTML
before any JavaScript runs.
**Cons:** components cannot be written freely inside prose; every figure goes
through the tag registry. A remark/rehype pipeline is more setup than mdsvex.

## Decision

We choose **Option C**. The Markdown source is the contract that the gates,
the tests, `llms.txt` and agents all read. Keeping it plain is what lets the
site gain interaction without any of those losing sight of the content.

Six rules come with it.

1. **Figures render real output, generated at build time.** A Rust example
   (`examples/docsite_figures.rs`) runs the released pipeline over fixed inputs
   and writes JSON under `site/src/lib/figures/`. The JSON is committed. A
   gate regenerates it and diffs, the same way gate 6 treats `llms.txt`. A
   change in matra's output then shows up in review as a changed figure, which
   makes the figure data a regression artifact as well as documentation.
2. **Every figure has a text twin.** The same data renders as a table or a
   structured list alongside, or under a disclosure, next to the graphic. The
   JSON is linked from the page. An agent, a screen reader and a reader
   printing the page all get the content without the graphic.
3. **Motion is for change only.** Animate transitions between two states the
   reader asked for, such as switching sentences, expanding a subtree, or
   comparing metrics before and after an edit. At most two stages of about a
   second, easing in and out. No motion that starts on its own, no ambient
   loops, no parallax. Under `prefers-reduced-motion` a figure jumps straight
   to its end state. This is a house rule and stricter than WCAG, and it is
   stated as ours.
4. **d3 computes; Svelte draws.** Use d3's layout and math modules
   (`d3-hierarchy`, `d3-scale`, `d3-shape`, `d3-force` run to rest at build
   time). Svelte owns the DOM and transitions. Not `d3-selection` or
   `d3-transition`, so there is one rendering model and figures prerender.
5. **The familiar form comes first.** Wherever a graphic uses an encoding a
   newcomer may not know, such as a dependency tree, the page leads with a
   plain table or sentence-level reading and offers the graphic as the next
   step. Predict-then-reveal is allowed in explanation pages, where readers are
   new, and never in reference pages.
6. **URLs do not change.** SvelteKit's default `trailingSlash: 'never'` with
   `adapter-static` prerenders `/guides/cli` as `guides/cli.html`, the same
   paths mdBook serves. rustdoc stays at `/api/`.

### Layout

- `site/` holds the SvelteKit app (`adapter-static`, prerender everything).
- `site/content/` holds the Markdown, moved from `book/src/` with `git mv` so
  history follows. `SUMMARY.md` stays the navigation source, so `llms.txt`
  generation and gate 2 keep their input format.
- `book/` is removed once the new site passes every gate.
- Search: Pagefind, indexed from the built HTML.

### Gates, ported one for one

| Gate today | Under this ADR |
|---|---|
| 1 Links resolve (lychee over `book/src`) | lychee over `site/content` and over the built HTML |
| 2 Every page in `SUMMARY.md` | Same, over `site/content`, and it follows symlinks: `roadmap.md` is one, and today's gate skips it |
| 3 Type names resolve in `src/` | Same, over `site/content`; figure JSON is exempt, since it is output rather than prose |
| 4 `mdbook build` has no warnings | `svelte-check` and `vite build` fail on any warning; every tag in the content must be in the registry |
| 5 No em dashes | Same, over `site/content`, following symlinks |
| 6 `llms.txt` current | Same generator, retargeted at `site/content/SUMMARY.md` |
| new: figures current | Regenerate figure JSON and diff |
| new: every figure has a twin | Each registered figure component must render its text form; checked by a test over the prerendered HTML |

`tests/cited_figures.rs`, `tests/error_tables.rs` and
`skills/matra/references/semantic.md` read pages by path. They move to the new
paths in the same PR as the `git mv`, and the pinned digests do not change,
since the files do not.

## Consequences

- **Positive:** figures show real, current output and fail review when it
  changes. The site gains search, component reuse and prerendered HTML.
  Agents and the gates keep reading plain Markdown.
- **Negative:** a Node toolchain joins a Rust and Python project, with its own
  lockfile, Dependabot ecosystem and supply-chain exposure (ADR-0005 applies:
  pinned versions, lockfile committed, `npm ci`). The figure-currency gate needs
  the UDPipe model in the docs job, which adds a pinned, hash-verified download
  (ADR-0011).
- **Neutral:** the tag registry is the one place a new kind of figure is added.
  That is a small cost to a writer and keeps the set of figures reviewable.

## Validation

- **Parity before features.** The first cut-over ships the current 26 pages
  with no new figures, and every gate passing, before any figure lands. If the
  port cannot reach parity, the migration stops there.
- **Agent reading.** An agent given only `llms.txt` and the site answers the
  same set of questions about matra as it does today, without loss. A figure
  whose content an agent cannot recover from its text twin fails this.
- **Readers.** Self-reports such as "that was clear" are not evidence. The
  first figures are judged by whether a new reader can answer a specific
  question about matra's output faster and more correctly with the figure than
  with the table alone. If the table does as well, the figure is removed.
- **Revisit** if parsing becomes available on `wasm32`, which would make live
  figures possible and change rule 1.
